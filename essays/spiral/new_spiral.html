Новый виток: диалектика программирования в эпоху AI-harness

Эссе о том, как примитивы программирования возвращаются на новом витке спирали — и где в этой картине место агентным harness-движкам.

0. Один закон, из которого выводится всё остальное

Прежде чем сопоставлять «цикл → goal» и «функцию → skill», нужно найти сам закон спирали — иначе получится не диалектика, а словарь синонимов. Закон такой:

Возврат естественного языка через отрицание формального.

Три такта большого витка:

  • Тезис — непосредственность. До машин человек выражал намерение на естественном языке: «построй дом». Намерение богатое, контекстное, но неисполнимое само по себе — его несёт исполнитель-человек, который доформулирует недосказанное.
  • Антитезис — отчуждение. Чтобы намерение исполняла машина, естественный язык пришлось отбросить и принять формальный: точный, однозначный, детерминированный — и отчуждающий. Программист теперь думает как машина, вплоть до указателей и malloc. Выразительность принесена в жертву точности. Вся башня абстракций (asm → C → ООП → DSL/SQL) — это медленный подъём обратно: каждый слой отвоёвывает у «как» немного «что».
  • Синтез — опосредованная непосредственность. AI-harness возвращает естественный язык — «сделай X» снова исполнимо. Но это не наивный возврат к тезису: под естественным языком лежит вся формальная башня. Намерение снова конкретно (как в тезисе), но теперь опосредовано схемами, тестами, типами, памятью. Формальные языки не удалены — они работают снизу, harness компилирует намерение сквозь них.

Это и есть снятие (Aufhebung): формальное отменено как обязательная поверхность, сохранено как исполняющий слой и поднято на уровень, где им управляет намерение.

И ключевое: каждое частное соответствие ниже — это один и тот же ход в миниатюре. Любой примитив проходит путь естественный → формальный → исполнимо-естественный, и формальная версия не исчезает, а уходит «под капот». Поэтому дальше — не пары, а триады.

1. Управление потоком

Цикл

  • Тезис: «работай, пока не будет готово» — человеческая, расплывчатая воля.
  • Антитезис: while (cond) { body } — нужно формализовать условие выхода, тело и счётчик. Точно, но всю логику выхода несёт на себе программист.
  • Синтез: цель (/goal) + критерий готовности (DoD). Намерение цикла снова заявляется на естественном языке, но терминальность обеспечивает формальный судья — DoD-чеклист или LLM-классификатор. while никуда не делся: он крутится снизу как шаговый цикл агента (tool call → результат → решение).
  • Что сохранилось снизу: счётчик итераций → бюджет токенов; инвариант цикла → инварианты конфигурации; тело → описание шага в цели.
  • Новое качество: условие выхода стало вероятностным суждением с аргументацией, а не булевым cond.

Ветвление

  • Тезис: «смотря по обстоятельствам» — человеческое усмотрение.
  • Антитезис: if x > 5 {...} else {...} — обстоятельства сведены к булеву предикату.
  • Синтез: LLM-роутер/классификатор. Снова «смотря по смыслу», но решение принимает модель-судья: «это новая проблема или уже известная?» → завести задачу или решить на месте. if сохранён внутри как маршрутизация между ветвями; новое качество — семантика вместо предиката.

2. Состояние и память

Самый богатый узел: формальный урок здесь — область видимости (scope) — целиком переносится в синтез как дисциплина файлов.

  • Тезис: человек просто помнит — «мы же договорились про X».
  • Антитезис: объявленные переменные с жёстким scope + ручное управление памятью (malloc/free). Память точная, но отчуждённая: программист вручную решает, что живёт и что освобождать.
  • Синтез: память снова на естественном языке (конфигурационные и memory-файлы агента), но дисциплина scope сохранена как иерархия файлов:
Scope (формальный урок) Антитезис Синтез (AI-harness)
Локальная (стек) int x в функции In-context: факты текущего разговора
Глобальная global config Конфиг проекта (правила, DoD, запреты)
Статическая / межмодульная static Сквозная память — cross-session, cross-project
Персистентная БД, файлы Живые документы — backlog, контракт цикла
Внешняя env vars Секреты, бюджет API, ключи
  • Сборка мусора возвращается как семантика: суммаризация и вытеснение из контекстного окна — это GC, но решение «что освободить» принимается по смыслу, а не по достижимости ссылок.
  • Новое качество: scope теперь = область применимости знания, а не область видимости имени. Это разворачивается в раздел 9.

3. Абстракция: функции и типы

Функция → Skill

  • Тезис: «обычный наш способ делать X» — именованная человеческая привычка.
  • Антитезис: def f(typed args) -> typed return — привычка формализована в сигнатуру с типами.
  • Синтез: Skill / инструмент с описанием. Снова именованная способность на естественном языке (когда применять + примеры), но сигнатура сохранена: у инструмента есть JSON-схема параметров, у навыка — контракт-описание. Именованные операции (review, goal, run) вызываются по известному контракту. Новое качество: тело вероятностное, «return» — артефакт или текст.

Система типов → Structured Output

  • Тезис: неформальное ожидание «тут будет дата».
  • Антитезис: статические типы, проверка компилятором — отчуждённая строгость над байтами.
  • Синтез: JSON Schema / structured output. Типы возвращаются, проверяются на границе вызова инструмента, но теперь типизируют семантическое содержимое, а не раскладку памяти. Это тот самый возврат формализма (см. раздел 8) — но локально, на каждом вызове.

4. Структуры данных

Здесь снятие тоньше: классическая структура не «заменяется», а становится способом организации намерений и состояния.

Классика Снятие в harness Операции
Массив / список Backlog — упорядоченные задачи push (новая задача), pop (в работу), iterate
Стек (LIFO) Контекстное окно: свежее — в фокусе LIFO-приоритет недавнего
Очередь (FIFO) Очередь фоновых агентов агент берёт по порядку
Хеш-таблица Конфиг: ключ-слово → правило lookup правила по триггеру в промпте
Дерево Декомпозиция: фазы → задачи → подзадачи обход в глубину = раскрытие
Граф (DAG) Зависимости задач (depends_on) топосортировка → порядок работы
Trie (бор) Пространство команд prefix-matching команд
Префиксные суммы / дерево отрезков Checkpoint-ы прогресса каждый закрытый цикл — сохранённый префикс

Рекурсия

  • Антитезис: функция зовёт себя, база — условие останова.
  • Синтез: вложенные агенты (workflow → agent → sub-agent → tool). База рекурсии = терминальный инструмент (read/write/bash). Стек вызовов = дерево агентов. Мемоизация возвращается как prompt cache; динамическое программирование — как переиспользование решений прошлых итераций через память и backlog: нашли проблему → задокументировали решение → следующий цикл не переоткрывает.

5. Ресурсы, сложность и контракты

RAM-модель → ресурсная модель агента

Анализ сложности не исчезает — меняются оси ресурсов:

RAM-модель Модель агента
Время Latency LLM (p50/p95), длина агентского цикла
Память Контекстное окно (токены), размер сквозной памяти
— (новое) Стоимость ($/1M токенов) — ось, которой не было
Параллелизм Concurrent agents (типичный cap ≈ числу ядер)

Нижняя оценка задачи сохраняется буквально: есть структурно невыполнимое. Задача, чьи входные данные не помещаются в контекстное окно целиком, упирается в предел ресурса так же, как O(n²) на n=10⁶ упирается во время, — это не дефект реализации, а граница модели вычислений.

Инварианты, пред/постусловия → DoD

  • Антитезис: formal verification, assertions, Design by Contract (Hoare logic, TLA+) — строгая, но отчуждённая спецификация.
  • Синтез: DoD (Definition of Done) как семантический контракт. Pre-condition → «что должно быть готово до старта»; post-condition → DoD-чеклист (тесты зелёные, метрика ≥ порога, документация обновлена); инвариант → «бюджет не превышен, дизайн-токены не менялись, секреты не закоммичены». Формальный контракт вернулся, но проверяется по смыслу + машинно-проверяемыми кусками.

6. Асинхронность

  • Антитезис: async/await, корутины, потоки, mutex.
  • Синтез: фоновые автономные агенты (recurring loops, cron-триггеры; класс автономных агентов, которые читают issues → правят → открывают PR по расписанию).
  • mutex → turn-taking (последовательные вызовы, где нужна атомарность)
  • thread pool → параллельный пул агентов с лимитом одновременности
  • event loop → cron / recurring-trigger
  • race condition → конфликт параллельной записи → решается изоляцией (отдельный worktree на агента)

Направление — фоновые агенты как производственная практика — наблюдается уже у нескольких независимых систем, и open-source, и внутрикорпоративных. Конкретные публичные метрики охвата здесь вторичны; важно само направление: автономный агент, работающий по расписанию рядом с командой, перестал быть экзотикой.

7. Где место новым фишкам harness — там, где синтез ещё не завершён

Диалектика не только описывает прошлое — она предсказывает пробелы. Пробел всегда там, где мы уже вернулись к естественно-языковому намерению, но формальный слой под ним ещё не достроен. Это и есть карта того, что harness-движкам предстоит отрастить:

Формальный инструмент, который «вернётся» Чего пока нет Зародыш, который уже видно
Отладчик Есть трейс инструментов, нет трейса намерений — почему агент так решил логи tool-calls, transcript
Компилятор/тайп-чекер целей Нет статической проверки, что цель + DoD совместны и достижимы до траты токенов DoD-чеклисты вручную
Линкер + GC памяти Нет авторазрешения связей и детекции протухших фактов между файлами памяти [[wikilinks]] в памяти, ручная ревизия
Пакетный менеджер навыков Навыки — это функции, но нет версионированного реестра с разрешением зависимостей lock-файлы для наборов навыков — первые ласточки
Тест-фреймворк для вероятностных функций Как юнит-тестировать навык, чья реализация недетерминирована eval-харнессы, бенчмарки
Транзакции / rollback Нет ACID над действиями агента; «откатить шаг» = вручную worktree-изоляция — зачаток атомарности

Практическая выжимка: новые возможности harness ложатся не куда угодно, а в недостающие формальные слои синтеза. Каждая строка таблицы — кандидат на следующую значимую фичу.

8. Куда это ведёт

Все векторы — это достраивание синтеза до конца: вернуть формальную мощь под естественно-языковую поверхность.

  1. AgentOS. Harness дорастает до операционной системы: планировщик, менеджер памяти, спавнер процессов. Термин уже звучит в исследованиях — пока как направление, а не зрелый стандарт.
  2. Компилятор намерений. Сейчас harness — интерпретатор (каждый вызов сам по себе). Следующий шаг — статический анализ «цель + DoD» до запуска: план, оценка стоимости, предупреждение о конфликте инвариантов. (= строка «тайп-чекер целей» из раздела 7.)
  3. Декларативный язык задач. SQL победил, потому что задаёт что, а не как. Аналог для агентов — стандартный DSL Goal + Constraints + DoD + Context, переносимый между движками.
  4. Инверсия контроля. От «человек инициирует → агент исполняет» к «агент находит работу и предлагает → человек апрувит». Машина становится основным автором, человек — ревьюером и носителем намерения.
  5. Возврат формализма (главный диалектический пуант). Мы ушли от Hoare logic к неформальным промптам — и спираль тянет назад к строгости: JSON Schema, DoD-чеклисты, structured output, eval-харнессы. Но это возврат на новом уровне: верифицируется семантика, а не синтаксис. Точно то, чем закрывается большой виток из раздела 0.

9. Организация памяти

Принцип — прямое следствие раздела 2: scope памяти = область применимости знания (а не видимости имени).

        [in-context]   текущий разговор — исчезает с сессией
             ↑
   [сквозная память]   паттерны для ЛЮБОГО проекта
                       (feedback, предпочтения, cross-project инсайты)
             ↑
     [конфиг проекта]  стек, DoD, запреты, команды, инварианты
             ↑
  [живые документы]    backlog, контракт цикла, лог анализа —
                       текущее состояние работы
             ↑
       [.env, config]  секреты и runtime (не для агента в открытую)

Куда класть: - Сквозная память — паттерн поведения, предпочтение, cross-project инсайт. Критерий: нельзя переоткрыть из кода и применимо за пределами одного проекта. - Конфиг проекта — стек, бюджет, дизайн-токены, DoD проекта, команды, запреты. - Backlog — задачи, статус итерации, known issues. Живой, не архив. - Контракт цикла (DoD) — стабилен до конца цикла, меняется только между Major-версиями (см. семантическое версионирование циклов ниже).

Чего НЕ класть в сквозную память: конкретный код (протухает), списки PR / activity (это git), текущие TODO (это backlog), архитектурные решения (это конфиг проекта или код).

Семантическое версионирование циклов: Major = смена цели; Minor = закрыт цикл (DoD выполнен); Patch = hotfix без закрытия DoD.

Гигиена памяти как GC: если файл памяти называет файл, флаг или функцию — перед опорой на него стоит проверить, что они ещё существуют. Память отражает момент записи, не «сейчас». Это и есть тот самый недостающий «GC + линкер» из раздела 7, пока исполняемый вручную.

10. Bootstrap-документ проекта

Отдельная практика, которая напрашивается из всей картины, — bootstrap-документ: аналог init() для проекта. Один файл, который агент читает первым и получает «операционную систему» проекта: суть, стек, запреты и разрешения, структуру backlog, DoD по умолчанию, инварианты, команды, ресурсные лимиты.

Его связь с конфигом проекта диалектична: bootstrap — стартовый снимок (заполняется один раз при запуске), конфиг проекта — живой документ (эволюционирует по ходу работы). Граница между ними — один из открытых вопросов ниже.

Минимальный скелет такого документа:

1. Суть проекта (1 абзац)
2. Стек (backend / frontend / провайдер модели / бюджет)
3. Запрещено агенту (DO NOT) — pre-condition assertions
4. Разрешено без подтверждения
5. Структура backlog (формат задачи, depends_on, правило роста)
6. DoD по умолчанию (post-condition)
7. UI/UX правила (если есть)
8. Ключевые команды
9. Ресурсные лимиты (контекст / стоимость / параллелизм)
10. Инварианты (что не должно меняться)

11. Открытые вопросы для следующих витков

  • Как агент должен обнаруживать нарушение инварианта (аналог assertion violation), а не молча его переступать?
  • Можно ли построить отладчик намерений — трейс «почему решил», а не трейс инструментов?
  • Что такое юнит-тест для навыка — функции, которая вероятностна? Достаточно ли eval-харнесса?
  • Где точная граница между конфигом проекта и bootstrap-документом — стартовый снимок vs живой конфиг?
  • Нужен ли памяти семантический changelog (версионирование знания, а не только кода)?
  • Если синтез = «формальное под капотом естественного», то какой следующий антитезис эту пару отбросит? Витков всегда больше одного.
